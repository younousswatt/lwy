# Projet final — Application CLI

Ce projet final consiste à réaliser un gestionnaire de tâches utilisable depuis le terminal. L'application permet d'ajouter des tâches, de les lister, de les marquer comme terminées et de les supprimer. Les données sont enregistrées dans un fichier JSON pour survivre à la fermeture du programme.

Le projet réunit les compétences du parcours : fonctions, structures de données, exceptions, fichiers, classes, imports, packages, tests et interface en ligne de commande. À la fin, vous aurez une application organisée, exécutable et documentée.

## Objectifs

- Concevoir une application CLI avec des commandes cohérentes.
- Organiser le code en package et séparer interface, logique métier et stockage.
- Représenter les tâches avec une classe.
- Lire et écrire des données JSON en traitant les erreurs.
- Tester la logique métier et les cas limites.
- Installer et exécuter le package dans un environnement virtuel.
- Rédiger une documentation d'utilisation claire.

## Prérequis

- Tous les modules précédents du parcours Python, en particulier le module 8 sur les modules et packages.
- Python 3.10 ou version ultérieure.
- Un terminal, un éditeur de code et les commandes `python` et `pip`.

## Cours

### Cahier des charges

Le gestionnaire de tâches doit permettre de :

- ajouter une tâche à partir d'un titre non vide ;
- afficher toutes les tâches avec leur identifiant et leur état ;
- marquer une tâche existante comme terminée ;
- supprimer une tâche existante ;
- conserver les données entre plusieurs exécutions ;
- signaler clairement les commandes invalides, les identifiants inconnus et les erreurs de fichier.

Les tâches sont locales à l'utilisateur. Aucun service web ou compte n'est nécessaire.

### Architecture

Séparez le programme en trois responsabilités :

- `models.py` définit la représentation d'une tâche et les opérations métier ;
- `storage.py` convertit les tâches en JSON et gère les erreurs d'accès aux données ;
- `cli.py` interprète les commandes et affiche les résultats.

```text
todo-cli/
├── pyproject.toml
├── README.md
├── src/
│   └── todo_cli/
│       ├── __init__.py
│       ├── __main__.py
│       ├── models.py
│       ├── storage.py
│       └── cli.py
└── tests/
    └── test_models.py
```

L'interface dépend de la logique et du stockage, mais le modèle ne dépend pas du terminal. Cette séparation permet de tester les règles métier sans simuler des commandes.

### Modèle d'une tâche

Une tâche contient un identifiant, un titre et un état. `dataclass` fournit l'initialisation et la représentation de base de l'objet.

```python
# src/todo_cli/models.py
from dataclasses import dataclass


@dataclass
class Task:
    id: int
    title: str
    done: bool = False
```

Le gestionnaire regroupe les opérations métier :

```python
class TaskManager:
    def __init__(self, tasks=None):
        self.tasks = list(tasks) if tasks is not None else []

    def add(self, title):
        title = title.strip()
        if not title:
            raise ValueError("Le titre ne peut pas être vide")

        next_id = max((task.id for task in self.tasks), default=0) + 1
        task = Task(id=next_id, title=title)
        self.tasks.append(task)
        return task

    def list_tasks(self):
        return list(self.tasks)

    def complete(self, task_id):
        for task in self.tasks:
            if task.id == task_id:
                task.done = True
                return task
        raise ValueError(f"Aucune tâche avec l'identifiant {task_id}")

    def delete(self, task_id):
        for index, task in enumerate(self.tasks):
            if task.id == task_id:
                return self.tasks.pop(index)
        raise ValueError(f"Aucune tâche avec l'identifiant {task_id}")
```

L'identifiant suivant est calculé à partir de l'identifiant maximal présent, et non du nombre de tâches. Après une suppression, cette règle évite de réutiliser immédiatement un identifiant encore présent.

### Persistance JSON

Le fichier de données est une liste d'objets JSON. Le module de stockage isole les conversions et les erreurs de fichier du reste de l'application.

```python
# src/todo_cli/storage.py
import json
from pathlib import Path

from .models import Task


class StorageError(Exception):
    """Erreur de lecture ou d'écriture du fichier de tâches."""


def load_tasks(path):
    file_path = Path(path)
    if not file_path.exists():
        return []

    try:
        data = json.loads(file_path.read_text(encoding="utf-8"))
        if not isinstance(data, list):
            raise ValueError("La racine du fichier doit être une liste")

        tasks = []
        for item in data:
            if not isinstance(item, dict):
                raise ValueError("Chaque tâche doit être un objet")
            tasks.append(Task(**item))
        return tasks
    except (OSError, json.JSONDecodeError, TypeError, ValueError) as error:
        raise StorageError(f"Impossible de lire {file_path} : {error}") from error


def save_tasks(path, tasks):
    file_path = Path(path)
    data = [
        {"id": task.id, "title": task.title, "done": task.done}
        for task in tasks
    ]
    try:
        file_path.write_text(
            json.dumps(data, ensure_ascii=False, indent=2),
            encoding="utf-8",
        )
    except OSError as error:
        raise StorageError(f"Impossible d'écrire {file_path} : {error}") from error
```

`ensure_ascii=False` conserve les caractères accentués lisibles dans le fichier. Une erreur de format ou de permissions devient une `StorageError` explicite, que l'interface pourra afficher à l'utilisateur.

<Callout type="warn">
Le fichier JSON est une entrée externe : il peut être vide, tronqué, modifié manuellement ou contenir une structure inattendue. Ne transformez pas une erreur de lecture en liste vide, car cela ferait croire que les données ont disparu puis risquerait de les écraser.
</Callout>

### Construire une interface avec `argparse`

`argparse` est inclus dans Python. Il permet de définir les commandes et de produire automatiquement une aide. Une option `--file` permet de choisir le fichier de données.

```python
# src/todo_cli/cli.py
import argparse
import sys

from .models import TaskManager
from .storage import StorageError, load_tasks, save_tasks


def build_parser():
    parser = argparse.ArgumentParser(description="Gérer une liste de tâches")
    parser.add_argument(
        "--file",
        default="tasks.json",
        help="chemin du fichier de données (défaut : tasks.json)",
    )
    commands = parser.add_subparsers(dest="command", required=True)

    commands.add_parser("list", help="afficher les tâches")

    add_parser = commands.add_parser("add", help="ajouter une tâche")
    add_parser.add_argument("title", help="titre de la tâche")

    complete_parser = commands.add_parser("complete", help="terminer une tâche")
    complete_parser.add_argument("id", type=int, help="identifiant de la tâche")

    delete_parser = commands.add_parser("delete", help="supprimer une tâche")
    delete_parser.add_argument("id", type=int, help="identifiant de la tâche")

    return parser
```

L'option globale `--file` doit être placée avant le nom de la commande, par exemple `python -m todo_cli --file mes-taches.json list`.

La fonction `main` relie l'interface au modèle et au stockage :

```python
def main():
    parser = build_parser()
    args = parser.parse_args()

    try:
        manager = TaskManager(load_tasks(args.file))

        if args.command == "add":
            task = manager.add(args.title)
            save_tasks(args.file, manager.list_tasks())
            print(f"Tâche ajoutée : [{task.id}] {task.title}")

        elif args.command == "list":
            tasks = manager.list_tasks()
            if not tasks:
                print("Aucune tâche. Ajoutez-en une avec la commande add.")
            for task in tasks:
                status = "x" if task.done else " "
                print(f"[{status}] {task.id} - {task.title}")

        elif args.command == "complete":
            task = manager.complete(args.id)
            save_tasks(args.file, manager.list_tasks())
            print(f"Tâche terminée : [{task.id}] {task.title}")

        elif args.command == "delete":
            task = manager.delete(args.id)
            save_tasks(args.file, manager.list_tasks())
            print(f"Tâche supprimée : [{task.id}] {task.title}")

        return 0
    except (StorageError, ValueError) as error:
        print(f"Erreur : {error}", file=sys.stderr)
        return 1
```

Enregistrez `main` dans `cli.py`. Les commandes qui modifient les données appellent `save_tasks` après la modification ; la commande `list` ne réécrit pas le fichier. L'erreur est affichée sur la sortie d'erreur et la fonction renvoie un code de sortie non nul.

### Tester la logique métier

Les tests du gestionnaire ne dépendent pas du terminal ni du fichier JSON :

```python
# tests/test_models.py
import unittest

from todo_cli.models import TaskManager


class TaskManagerTests(unittest.TestCase):
    def test_add_creates_task_with_next_id(self):
        manager = TaskManager()

        task = manager.add("  Réviser Python  ")

        self.assertEqual(task.id, 1)
        self.assertEqual(task.title, "Réviser Python")
        self.assertFalse(task.done)

        manager = TaskManager()

        with self.assertRaises(ValueError):
            manager.add("   ")

        manager = TaskManager()

        with self.assertRaises(ValueError):
            manager.complete(42)


if __name__ == "__main__":
    unittest.main()
```

## Erreurs fréquentes

**Tout placer dans `cli.py`**

Quand les règles métier, les accès fichiers et les affichages sont mélangés, il devient difficile de tester et de faire évoluer le programme. Gardez des modules avec une responsabilité claire.

**Écraser les données si la lecture échoue**

Un JSON invalide n'est pas la même chose qu'un fichier absent. Le fichier absent peut représenter une nouvelle liste vide ; un fichier illisible doit produire une erreur visible et ne pas être réécrit silencieusement.

**Ne pas sauvegarder après une modification**

Une tâche ajoutée uniquement en mémoire disparaît à la fin du processus. Chaque opération qui modifie la liste doit persister le nouvel état.

**Réutiliser un identifiant après une suppression**

Utiliser `len(tasks) + 1` peut créer des doublons. Calculez le prochain identifiant à partir du plus grand identifiant existant.

**Ne pas traiter une tâche inexistante**

Une commande avec un identifiant inconnu doit produire un message compréhensible et un code de sortie d'échec, pas une erreur de programmation ni un succès trompeur.

**Confondre nom du package installé et nom importé**

Le nom de distribution `todo-cli-lwy` peut être différent du nom Python `todo_cli`. Le premier est déclaré dans `pyproject.toml`, le second correspond au package importable sous `src/`.
